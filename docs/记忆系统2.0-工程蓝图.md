# 记忆系统 2.0 工程蓝图（v2.2 统一记忆系统版）

> 版本：v2.2 ｜ 2026-09-05
> 架构决策：**只有一个记忆系统**，向量记忆作为其内部可选模块（默认关）；记忆系统的全部 LLM/嵌入调用走**独立副 API**，不占用主对话渠道。
> 对标：DlSNlGHT/World（滚动合并、总述规范、hash 校验、抽样）、柏宝书（账本套件、副 API、可选向量定位）。

---

## 0. 总体架构

```
┌─────────────────────────── 记忆系统（storyEngine）───────────────────────────┐
│  通道：副API（memoryApi，独立 url/key/model，未配置时跟随主API）               │
│                                                                              │
│  核心（始终启用）                       向量模块（calamity-memory-vec 开关）   │
│  ─────────────────                      ─────────────────────────────────    │
│  每层纪要 summary store                 嵌入服务（独立嵌入配置）              │
│  编年史 chronicle（每层一行）            摘要向量库 embeddings store           │
│  滚动合并：纪事→卷宗→典章 story          向量召回（余弦 Top-K，指纹失效管理）   │
│  词法检索（gameData 名词表兜底）         检索展开 = 向量召回 ∪ 词法命中（去重） │
│  注入管线（五块固定 + 检索块）                                                │
│  撤销联动 / 查看器                                                            │
└──────────────────────────────────────────────────────────────────────────────┘
```

- 向量模块开启：检索展开块走"向量 ∪ 词法"双路合并（按楼层去重）；关闭：词法独挑。**其余管线完全一致**——常驻线（典章/卷宗/纪事/编年史尾窗）与向量无关。
- 副 API 承载的记忆系统调用：三级压缩、（P1）主观记忆提取、（P1）台账维护辅助。主对话 API 只负责叙事本身。
- 嵌入调用沿用独立嵌入配置（embedding-service 现有机制），逻辑上也属于记忆系统通道。

## 3. 数据模型与模块

### 3.1 新 IDB 库 `calamity-memory` v1（module/memory-store.js，~150 行）

```js
summary:   { keyPath: 'floor' }    // 每层纪要全文（压缩输入 + 命中展开源）
chronicle: { keyPath: 'floor' }    // 编年史一行（主键=楼层号）
story:     { keyPath: 'id' }       // 纪事/卷宗/典章（level 1/2/3 + absorbedBy）
embeddings:{ keyPath: 'id' }       // 向量模块：{id, floor, vector(ArrayBuffer), fingerprint, createdAt}
```

- summary：`{floor, text(本层全部 SUMMARY 以'；'连接), time:'300年11月14日 14:30', location, createdAt}`
- chronicle：`{floor, time, location, text(≤40字), createdAt}`，渲染 `第87层｜300年11月14日 14:30·铁矿镇｜…`，同日省略日期段
- story：`{id:'st_l1_…', level, from, to, text:'【第81~100层·纪事】…', absorbedBy, createdAt}`
- embeddings：仅向量模块开启时写入；`fingerprint` 用于换嵌入模型后作废旧向量

旧 `calamity-vecmem` 库惰性留存（不读不写）；提供「迁移旧向量」按钮（把仍有效的 L0 记录按 floor 映射进新库，可选）与「清除旧数据」按钮（P2）。

### 3.2 localStorage 键

| 键 | 默认 | 说明 |
|---|---|---|
| `calamity-memory-enabled` | `'1'` | 记忆系统总开关 |
| `calamity-memory-vec` | `'0'` | **向量模块开关（默认关）** |
| `calamity-memory-api` | `null` | 副API配置 JSON `{baseUrl, apiKey, model}`，null=跟随主API |
| `calamity-memory-every` / `-keep1` / `-keep2` | 20 / 5 / 3 | 滚动合并参数 |
| `calamity-memory-floor` | 迁移自 `calamity-vec-floor-max` | 楼层号事实源 |
| `calamity-memory-pending` | `[]` | 压缩失败重试队列 |

### 3.3 副 API（module/memory-api.js，~80 行）

```js
window.memoryApi = {
  getConfig() {   // 副API配置，null 时回退主API配置
    try { return JSON.parse(localStorage.getItem('calamity-memory-api')) || apiService.getConfig(); }
    catch (e) { return apiService.getConfig(); }
  },
  async sendMessages(messages, options) {
    const cfg = this.getConfig();
    // 复用 apiService 的传输实现，但强制使用副API的 baseUrl/apiKey/model
    return apiService.sendMessages(messages, { ...options,
      baseUrl: cfg.baseUrl, apiKey: cfg.apiKey, model: cfg.model, _profile: 'memory' });
  }
};
```

- `apiService.sendMessages` 需小改：`options.baseUrl/apiKey` 存在时覆盖自身配置（约 5 行，向后兼容）。
- storyEngine 的所有 LLM 调用（压缩、主观记忆）一律走 `memoryApi.sendMessages`；嵌入调用走 embeddingService（其自身即独立渠道）。
- 设置页「记忆系统」节：副API 三项（留空=跟随主API）+ 向量模块开关 + 嵌入配置（迁移现有嵌入设置区）。

### 3.4 向量模块（收编现有代码）

- `embedding-service.js` / `legacy/memory-recall.js` 保留原实现；`vector-store.js` 的嵌入读写改指向 `calamity-memory.embeddings` store（或保留独立 vecmem 库亦可，二选一在步骤 1 定；**推荐**统一进新库，撤销与清除一个事务搞定）。
- 仅当 `calamity-memory-vec='1'` 且嵌入配置有效时：归档后异步向量化摘要；召回时参与合并。
- 指纹失效管理沿用现有机制；L2 事件层与 arc 压缩**不迁移**（分别由 P1 台账套件与滚动合并替代）。

## 4. 核心算法规格

### 4.1 词法检索（始终在场的召回通道）

```js
function lexicalRecall(userMessage, gd, topK = 3) {
  // 关键词源（全部来自 gameData）：relationships 人名、tasks 名称/目标、inventory 物品名、
  //   currentLocation + chronicle 出现过的 location 集合
  // 匹配：chronicle 行 text+location 子串命中计数 + userMessage ≥2字片段兜底
  // 排除：floor > floorMax - 9（已在逐字上下文，防重复）
  // 返回：得分>0 前 topK 楼层 → 各楼层 summary.text 全文
}
```

### 4.2 滚动合并状态机（状态全部由 story store 派生）

```js
async function maybeCompress(currentFloor) {
  if (_compressing || window._gameBusy) { queue(); return; }
  const every = +ls('calamity-memory-every') || 20;
  const l1 = allStory().filter(r => r.level === 1 && !r.absorbedBy);
  if (currentFloor % every === 0) {
    const from = currentFloor - every + 1;
    if (!l1.some(r => r.from === from))                    // 幂等：重试/重掷/撤销重推安全
      await compressStory(1, from, currentFloor, null);
  }
  const keep1 = +ls('calamity-memory-keep1') || 5;
  if (l1.length > keep1) {
    const b = l1.sort(byFrom).slice(0, keep1);
    await compressStory(2, b[0].from, b.at(-1).to, b);     // 5 纪事→1 卷宗
  }
  // 卷宗→典章同构（keep2=3）
}
// compressStory：memoryApi.sendMessages(COMPRESS_PROMPT(level), 输入=带楼层/时间锚点的行)
// 成功后 sources.forEach(markAbsorbed)（吸收≠删除，§6.3）；失败入 pending 队列下轮重试
```

### 4.3 压缩提示词（三级共用，字数上限注入；走副 API）

```
你是剧情记录员。将输入的按时间排列的剧情记录压缩成一段可脱离原文独立使用的
{纪事：150 字以内｜卷宗：400 字以内｜典章：600 字以内}的阶段纪事。

要求：
1. 写清关键行动如何引出后果、人物为何改变目标或立场、冲突如何升级或收束，
   保留具体人物、地点、物品与结果。
2. 已经完成、取消、失败或作废的事项与建立的事项同等重要，必须写明结局，
   禁止只留开端不留结局。
3. 禁止"局势变化了""经历了一系列事件""关系加深了"等空壳概括。
4. 怀疑、误解、声称保持人物认知表述，不得升级为世界事实。
5. 只依据输入，不补写未发生的情节。时间一律用输入给出的绝对时间
   （如"300年11月14日"），不得使用"三天前"等相对时间。

直接输出纪事正文，不要评论、标题或列表。
```

### 4.4 协议改动（输出格式.yaml `<SUMMARY>` 节，:289）

追加：`摘要须包含具体人名、物品名、地点名与事件结果，禁止"发生了冲突""有所进展"等无动作概括。摘要将进入本地记忆系统的编年史。`
楼层号/时间/地点一律本地标注（AI 数不准楼层），**不改输出结构**。改后重跑 `data-source/tools/convert-yaml-to-js.js`。

## 5. 主流程改造（index.html）

### 5.1 归档链（重写 :3921）

```js
async function storeSummariesToMemory(summaries) {
  const texts = (summaries || []).map(s => String(s).trim()).filter(s => s.length > 1);
  if (!texts.length) return 0;
  const floor = vecNextFloor();
  const gd = gameState.getGameData();
  await storyEngine.onTurnArchived({ floor, texts,
    time: fmtGameTime(gd.gameTime), location: gd.progress.currentLocation || '' });
  return texts.length;
}
// onTurnArchived：summary 入库 → chronicle 行 →（向量开启时）异步向量化入库
//              → 异步 maybeCompress()（fire-and-forget，互斥锁）
```

### 5.2 注入链（替换 :4152/4166）

```js
const blocks = await storyEngine.buildInjectBlocks(message, gd);
blocks.forEach(b => prompt.messages.splice(1, 0, { role: 'system', content: b }));
// buildInjectBlocks 依序（空则跳过）：
//   1.【世界纪事·典章】全部                        常驻
//   2.【世界纪事·卷宗】最近 keep2 篇                常驻
//   3.【世界纪事·最近纪事】最近 keep1 篇            常驻
//   4.【剧情编年史】最近 100 行                     常驻尾窗
//   5.【相关记忆召回】 向量开启: 向量召回∪词法(按楼层去重)；关闭: 词法   按需
```

**预算（A4）**：1000 层新增常驻 ≈ 典章 1800 + 卷宗 1200 + 纪事 750 + 尾窗 3000 + 纪要窗口 1600 + 检索块 600 ≈ **9850 字 ≈ 6400 token**；2000 层 ≈ 8000（典章慢增），对数增长。

### 5.3 撤销链（扩展 :3749/3776）

```js
// pushUndoSnapshot 追加：
memoryIds: storyEngine.snapshotIds(),   // {storyIds, summaryMax, chronicleMax, vecIds}
// undoLastTurn 追加：storyEngine.rollback(snap.memoryIds)
//   1. 删除快照后新产生的 story 记录
//   2. absorbedBy 指向已删记录者解除吸收（恢复注入与计数）
//   3. 删除 floor > summaryMax/chronicleMax 的 summary/chronicle
//   4. 向量开启时删除不在 vecIds 集合内的 embeddings 记录（沿用现有差量模式）
```

"吸收不删除"的原因：合并时若删源纪事，撤销跨合并边界（101→99 层）会造成前 100 层记忆真空；保留被吸收记录（不注入不计数）使回滚只翻标记，代价每 100 层 ~750 字。

## 8. 明确不做的事

- 不做"向量/词法"两套独立系统——向量是记忆系统内部的可选模块，管线只有一条。
- 不引入分词库——专名匹配只用 gameData 名词表 + 消息片段兜底。
- 不给 `<SUMMARY>` 加楼层号输出要求——楼层/时间/地点一律本地标注。
- 不做第 4 级"纪元史"（2000 层实测后再议）。
- 不迁移 L2 事件层与 arc（分别由台账套件、滚动合并替代）。
